# Register Bundled Crafts from the active release

A Bundled Craft compiles its Craft specification into its executable, so the digest its release pins also pins the declaration it presents, wherever the executable is installed. This amends ADR-0052 for Bundled Crafts: their `.jet/craft-spec.toml` stays the source file, but at runtime the declaration ships inside the executable rather than beside it. On every `serve` in a serving Plane with a trusted Security audit, and once the audit is trusted again if it was not, `jetd` reads the `manifest.json` beside its canonical executable and uses it only when it is for `jetd`'s own version. It copies each Bundled Craft, verified against the pinned digest, into the content-addressed Craft Artifacts (ADR-0072), and publishes `<id>.json` with SameUserExecutable trust and a core-only `bundled` origin, without a confirmation (ADR-0098), recording each change in the Security audit before it is published (ADR-0105). It replaces only an earlier bundled registration, never an installed Craft with the same id. Artifact collection keeps the digests that Runs in progress pin, so a release upgrade that moves the bundled default does not remove the Artifact an active Run restarts at (ADR-0018, ADR-0043, ADR-0088). `jetd` also gives each Craft and helper process it spawns a Harness search PATH: the PATH it inherited, then the well-known per-user and system Harness directories that exist and that no other user can write. This refines ADR-0013, ADR-0026 and ADR-0053.

## Rejected options

- **A per-Craft directory in the payload holding the declaration beside each executable.** Staging, the release script, Homebrew and both desktop packagers would all have to carry it, and the declaration would still be lost once the Craft is copied into `artifacts/<sha256>`, where every Craft shares one directory.
- **Pinning the Craft at its path in the payload.** `jetd core prune` and `brew cleanup` delete old versions, so a Run pinned to one could not restart its Craft, and the Capability snapshot lists only Crafts under `artifacts/`.
- **A new `CraftTrust` variant.** It is a wire type, and a `jetd` rolled back to before it could not read the bundled manifests, which would also stop Artifact collection.
- **A new audit actor for Jet releases.** An older `jetd` fails to read an unknown actor kind and would enter Security-degraded mode after a rollback; the registration reuses the actor that records Jet applying signed revocations, whose description now covers Jet applying its own release metadata.
- **Static PATHs in each service definition.** Every channel's unit or plist would need refreshing, Homebrew cannot name the user's home in its plist, and Harness-extension operations that a Craft launches itself would still miss the directories.
