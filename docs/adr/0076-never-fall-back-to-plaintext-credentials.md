# Never fall back to plaintext credentials

Jet stores only Credential references under `~/.jet`. macOS resolves them through Keychain; Linux probes the actual Secret Service D-Bus interface rather than merely checking for a package. If none is usable, the Linux GUI offers an explicit Set up secure storage action: where supported it asks PackageKit's session D-Bus service to install a reviewed provider appropriate to the detected distribution and desktop, displays the provider, package, source, and version first, and leaves authentication to the operating system. It never captures a privilege password or constructs a privileged shell command. Afterward it requires a successful create/read/delete probe before enabling durable Pairing; if PackageKit or the platform is unsupported, it shows exact manual instructions instead. `jetd` only reports and rechecks the capability and never invokes a package manager. Until verification succeeds, remote Pairing is session-only unless the user configures an external credential helper, and restart invalidates that pairing with a prominent warning. An established No-Visa connection may continue after the GUI closes, but every new or reconnected session authenticates again through the credential backend. `jetd` never prompts headlessly or retains an extractable long-term Client key; when the backend is locked, the Run enters `waiting_for_auth`, the GUI may initiate the operating-system unlock flow, and scheduled work remains pending only within its normal seven-day catch-up window. Jet otherwise permits session-only memory, SSH-agent identities, environment-provided native Harness authentication, or opaque external helpers and clearly reports the limitation. It never silently writes tokens, keys, passwords, or authentication callbacks into configuration, SQLite, Artifacts, diagnostics, or Recovery bundles. This applies ASVS 13.3.1 and 13.3.2; implementation must keep provider selection and installation within reviewed distribution sources under ASVS 15.2.1 and 15.2.4.
